# 95ee5b8 검토 보고 (222646d 대비)

아래 내용은 제공된 소스·diff·테스트 코드만 정적으로 읽고 판단한 것입니다. 코드를 실행하거나 화면을 보지는 않았습니다. 재현 단계는 코드 경로를 따라 추론한 것이고, 각 항목에 사실·추론·미확인을 따로 표시했습니다.

## 종합 의견: **조건부 부합**

교과서는 외부 AI 채팅에 직접 첨부한다는 경계는 지켜졌습니다. "앱이 파일 내용이나 AI 실행을 확인한 것은 아님"이라는 표시, 근거가 없으면 완료로 보지 않는 처리, 점검 이력 보관도 대체로 의도대로 짜여 있습니다.

다만 결과 회차를 다루는 핵심 경로 두 곳에 문제가 있습니다.
- 결과 이름 입력란 하나가 "이름 수정"과 "새 결과 이름" 두 역할을 함께 맡고 있습니다.
- 결과 본문을 처음 붙여 넣는 것을 "본문 변경"으로 처리합니다.

이 때문에 이력이 잘못 붙거나, 같은 결과가 여러 회차로 쪼개집니다. 성취기준 보관본과 저장 데이터 검증이 맞물려 저장 작업 전체를 못 읽게 되는 경로도 하나 있습니다.

## 구체적 발견

### 1. [P1] 결과 이름 입력란이 "이름 수정"과 "새 결과 이름"을 겸해 이전 회차 이력이 덮어써짐
- **위치:** `index.html:1066`(입력 처리), `:665-671`(registerResult), `:905`(결과 지정 입력란), `:1127`(new-result)
- **재현:** 결과1.pdf로 점검을 시작합니다 → 판정과 근거를 입력합니다 → 같은 입력란에 새 파일 이름 결과2.pdf를 적습니다 → "새 결과로 점검 시작"을 누릅니다.
- **예상:** 1차 결과와 1차 점검 기록은 "결과1.pdf"로 남아야 합니다.
- **실제(사실):** 이름을 입력하는 순간 `resultRecord.name`과 `checkRecord.resultName`이 결과2.pdf로 바뀝니다. 그 상태 그대로 `resultHistory`와 `checkHistory`에 보관됩니다. 결과적으로 "1차 결과 · 결과2.pdf"라는 잘못된 기록이 남고, 원래 이름은 사라집니다. 검토 요청 탭(tab 3)과 이어 하기 화면에서 이름을 적어도 같은 일이 생깁니다.
- **테스트:** events 테스트가 바로 이 순서를 따라가지만, 보관된 기록의 이름은 검사하지 않습니다.
- **최소 수정안:** 입력란은 현재 회차의 이름 수정 전용으로 둡니다. "새 결과로 점검 시작"을 누를 때는 `prompt('새 결과의 파일 이름')`으로 새 이름을 따로 받습니다. 별도 입력란을 늘리지 않아도 됩니다.

### 2. [P1] 등록한 결과의 본문을 처음 붙여 넣기만 해도 "본문 변경"으로 처리되어 교사 점검이 요청에서 빠짐
- **위치:** `:1063`, `:641-643`, `:907-914`
- **재현:** 결과를 지정합니다 → "수정 필요"와 근거를 입력합니다 → 검토 탭에서 같은 결과의 본문을 붙여 넣습니다.
- **예상:** 같은 회차에 본문만 더해지고, 교사 점검은 검토 요청에 그대로 들어가야 합니다.
- **실제(사실):** 빈 값에서 내용이 생긴 것도 변경으로 봅니다. 그래서 `bodyChanged=true`가 되고 `archiveCheck()`로 현재 점검이 이력으로 옮겨갑니다. 그러면 검토·이어 하기 요청에서 "교사 점검 기록" 블록이 빠집니다.
  - 본문은 저장하지 않으므로, 새로고침하거나 자료를 바꾼 뒤 같은 본문을 다시 붙여 넣어도 같은 일이 반복됩니다.
  - 테스트에서도 같은 파일이 3차 회차가 됩니다(`events.test.cjs`의 `새 문항 본문` 이후 version 3). 즉 테스트가 이 동작을 정상으로 굳혀 두었습니다.
  - 본문을 직접 타이핑하는 경우에도 글자를 칠 때마다 비교가 일어납니다.
  - `bodyChanged` 상태에서도 요청문에는 "N차 결과" 표시와 새 본문이 함께 나갑니다. 즉 새 본문이 이전 회차의 이름표를 달고 전달됩니다. 이 상태에서 전달을 막지도 않습니다.
- **최소 수정안:**
  - 본문을 처음 넣을 때 `resultRecord.bodyKey`(길이와 간단한 해시)만 기록하고 점검은 보관하지 않습니다.
  - `bodyKey`가 이미 있고 값이 다를 때만 `bodyChanged`로 처리합니다. 비교는 `input`이 아닌 `change`(입력란을 벗어날 때) 시점에 합니다.
  - `bodyChanged` 상태에서는 결과 회차 블록을 "본문 변경 · 회차 미지정"으로 표시하거나, `transferIssue`로 전달을 막습니다.

### 3. [P1, 발생 빈도 낮음] 직접 입력 과목을 고치면 성취기준 보관본과 과목이 어긋난 채 저장되고, 새로고침하면 작업 전체가 읽기 불가가 됨
- **위치:** `:584-593`, `:422`, `:1071`(저장한 뒤에 미리보기를 갱신하는 순서), `:920`, `:450-452`
- **재현(추론):**
  - "기타 · 직접 입력" 상태에서 과목을 "과학"처럼 실제 과목명으로 적고 성취기준을 담습니다. 또는 과목명에 공백이 섞인 구버전 데이터가 이미 기준 코드를 갖고 있는 경우도 해당합니다.
  - 이 상태에서 과목 입력을 고치고 바로 창을 닫거나 새로고침합니다.
- **실제:**
  - `customSubject` 입력은 `setCurriculumContext`(바꿀지 묻고 기준을 해제하는 처리)를 거치지 않습니다.
  - `save()`가 먼저 실행되어 이전 과목의 보관본과 새 과목이 함께 저장되고, 그다음 `live()`가 보관본을 새 과목 기준(기준 0개)으로 다시 만듭니다. 이 과정에서 고정해 둔 원문도 사라집니다.
  - 다시 불러올 때 `load()`가 `curriculum archive` 오류를 던집니다. 그러면 자동 저장이 멈추고, 화면은 빈 상태가 됩니다.
  - 이때 복구용 키에는 작업 전체가 아니라 자료 하나의 JSON이 덮어써집니다.
- **최소 수정안:**
  - 직접 입력 과목의 변경도 `setCurriculumContext`를 거치게 합니다.
  - `load()`에서는 보관본의 형식만 검증합니다. 교육과정 연도·과목이 어긋난 경우는 오류를 던지지 말고 기존 `curriculumIssue()` 경고로 처리합니다.
  - `selectedStandards()` 안에서 기존 보관본을 덮어쓰지 않습니다(보관본이 없을 때만 새로 만듭니다).

### 4. [P2] 이번 배포로 기존 사용자의 모든 점검이 "조건 변경"으로 표시됨
- **위치:** `:635`(새로 생긴 제작·확인 순서 블록), `:618`, `:650-652`, `:637-640`, `:896`
- **사실:** 비교에 쓰이는 블록에 앱이 만드는 문구 두 가지가 들어갑니다. 새로 생긴 제작·확인 순서 블록(`procedure`)과, 이번에 문구가 바뀐 참고자료 첨부 안내 블록입니다. 이전에 저장된 `lastRequest`와 `checkRecord`에는 이 문구가 없습니다.
- **결과(추론):** 교사가 아무것도 바꾸지 않았는데도 다음이 모두 생깁니다.
  - "마지막 제작 요청 이후 조건이 바뀌었어요" 안내와 점검 판정 입력 차단
  - 기존 회차 요청에 "이전 조건과 구분하라"는 블록이 붙음
  - 새 결과를 등록해도 이전 요청 스냅샷을 쓰므로 처음부터 낡은 점검으로 표시됨
- **최소 수정안:**
  - 비교할 때 `procedure` 블록을 빼고, 스냅샷에 앱 문구 버전을 기록합니다.
  - 앱 문구 버전만 다른 경우에는 "앱 문구 갱신 전 기록"이라고만 안내하고 판정 입력은 막지 않습니다.

### 5. [P2] 교과서 없이 만들기·발췌만 넣기·업무 문서에서 첨부 안내가 서로 어긋남
- **위치:** `:617-620`, `:887`
- **사실:**
  - `attachment = 수업 && 교과서 사용 || !!source` 조건 때문에, "이번에는 교과서 없이 만들기"를 골라도 자료·쪽수를 적으면 "교사가 직접 첨부합니다… 파일이 없으면 추측하여 진행하지 마세요"가 나갑니다.
  - 본문 발췌와 출처만 넣은 경우에도 AI는 파일이 첨부됐을 것으로 보고 파일을 요구하게 됩니다.
  - 가정통신문에서도 "교과서·참고자료"와 "단원·쪽수" 문구가 나옵니다.
- **추론:** 기본값이 "첨부"이고 선택란은 접힌 영역 안에 있습니다. 그래서 파일 없이 붙여 넣은 초보 교사는 AI가 진행을 멈추고 파일을 요구하는 상황을 겪을 수 있습니다.
- **최소 수정안:**
  - 조건을 `(수업 && 교과서 사용) || (source && !text)`로 바꿉니다.
  - "교과서 없이"를 고르고 발췌를 넣은 경우는 "발췌만 제공됨" 문구를 씁니다.
  - 업무 문서는 "참고자료"라고만 씁니다.
  - "추측하여 진행하지 마세요"는 "한 번 확인 질문하고, 선생님이 없이 진행하라고 하면 교과서 근거 없이 진행하되 [확인 필요]로 표시" 정도로 완화합니다. 버튼 추가는 필요 없습니다.

### 6. [P2] 이전 버전의 참고자료(`ctx.ref`)를 지울 수 없음
- **위치:** `:616`, `:887`, `:936`(more-context 목록에서 `ref` 제외), `:136`
- **사실:**
  - 이번 diff로 상황 단계의 참고자료 칸이 사라졌습니다.
  - 입력란과 요청문은 둘 다 `reference.source || ctx.ref`를 씁니다. 그래서 자료·쪽수 칸을 비워도 이전 값이 다시 표시되고 요청문에도 계속 남습니다.
  - 출처 확인 기준도 `ctx.ref` 때문에 자동으로 계속 켜집니다.
- **최소 수정안:** `load()`에서 `ctx.ref`를 `reference.source`로 한 번만 옮기고 `ctx.ref`는 삭제합니다. 이때 `source`가 비어 있을 때만 옮깁니다.

### 7. [P2] 낡은 점검이나 본문 변경 상태에서 근거 입력이 아무 안내 없이 버려짐
- **위치:** `:1064`, `:955`
- **사실:** 근거 입력란은 `state.check[k]`만 있으면 보입니다. 그런데 `staleCheck()`이거나 `checkRecord`가 없으면 입력 처리가 그냥 `return`합니다.
- **재현:** 판정을 입력합니다 → 상황 단계에서 학습 목표를 수정합니다 → 고치기 단계로 돌아와 근거를 입력합니다.
- **결과:** 입력은 저장되지 않고 안내도 없습니다. 새로고침하면 이전 내용으로 돌아갑니다.
- **최소 수정안:** 이 조건에서는 근거 입력란을 읽기 전용으로 만들고 "현재 조건으로 다시 점검 후 입력"이라는 안내를 붙입니다.

### 8. [P3] 초보자 화면의 중복과 판정 의미가 섞이는 부분
- **위치:** `:951`, `:1126`, `:686-687`
- **중복 버튼:** 요청문 화면에 "AI 결과를 받았어요 →"와 "AI 결과 확인하고 고치기 › 결과 확인하고 고치기"가 같은 곳(고치기 단계)으로 갑니다. 하나로 줄이면 됩니다.
- **수정 요청 자동 채우기:** "확인 불가"(교사가 확인하지 못함) 항목도 "고칠 점"으로 들어갑니다. 교사 판단과 수정 지시가 섞이므로 "확인 필요" 항목으로 따로 적는 것이 좋습니다.
- **완료 조건 안내:** 모든 기준을 "통과"로 표시해도 근거가 비어 있으면 일반 안내만 나옵니다. "근거 미입력 N개"처럼 남은 일을 구체적으로 알려 주면 좋습니다.

## 테스트가 놓친 경로
소스에 근거한 누락 사례입니다.
- 이름을 바꾼 뒤 새 결과를 등록했을 때 `resultHistory[0].name`과 `checkHistory[0].resultName`이 원래 이름을 유지하는지 (1)
- 등록 후 본문을 처음 붙여 넣었을 때 점검이 유지되는지, 새로고침 뒤 같은 본문을 다시 넣었을 때 회차가 늘지 않는지. 현재 테스트는 반대 동작을 정상으로 기대합니다 (2)
- 직접 입력 과목을 수정한 상태로 저장하고 다시 불러올 때 `loadIssue`가 생기지 않는지 (3)
- 이 커밋 이전 형식의 `lastRequest`를 넣고 불러왔을 때 `staleCheck()`가 어떻게 판정하는지 (4)
- 교과서 없이 만들기에 출처와 발췌를 넣은 경우, 업무 문서에 출처를 넣은 경우의 `referenceText()` 출력 (5)
- `ctx.ref`만 있는 구버전 데이터에서 자료·쪽수 칸을 비웠을 때 출력 (6)
- 낡은 점검 상태에서 근거를 입력했을 때의 처리 (7)

`newRequestState()`는 `standardArchive`를 지우지 않아 3번과 같은 문제를 일으킬 수 있습니다. 다만 현재 화면에 `data-act="new-request"` 버튼이 없어서 실제로는 실행되지 않는 코드입니다(미확인 리스크).

1. 모든 기준이 "통과"이고 근거까지 있어야 완료로 표시합니다(`:686`). 확인 불가를 통과로 바꾸지 않아 거짓 완료를 구조적으로 막습니다.
2. 요청문이 자신의 한계를 정직하게 밝힙니다. "이 요청문만으로 파일이 전달된 것은 아닙니다", "교사가 지정한 기록이며 앱이 파일 내용이나 AI 실행을 확인한 것은 아닙니다" 같은 문구가 있고, 앱이 실제 실행 하네스인 것처럼 홍보하지도 않습니다.
3. 회차와 점검을 덮어쓰지 않고 `resultHistory`·`checkHistory`에 보관합니다. 손상된 저장 데이터는 자동으로 덮어쓰지 않고 오류로 처리합니다. 성취기준 원문을 고정하는 동작도 테스트로 확인하고 있습니다.
