# 최종 집중 검토 (정적 읽기, 실행 안 함)

## 이전 P1 해결 여부 (코드상)

| 항목 | 판단 |
|---|---|
| 결과 이름을 바꿀 때 실제 라디오 체크 해제 | ✓ `archiveCheck`와 `querySelectorAll('chk-')` 해제가 함께 있음 |
| 첫 점검 전 옛 요청과 현재 조건이 다르면 차단 | ✓ `chk-` 핸들러의 `!checkRecord && lastRequest` 분기 |
| ‘현재 조건으로 다시 점검’이 새 기준으로 연결 | ✓ `recheck`가 `conditionSnapshot()`을 저장하므로 `staleCheck`가 false |
| 짧은 수정이 제작 조건을 갱신하지 않음 | ✓ `lastTransfer`와 `lastRequest`를 구분 |

## 남은 배포 차단 후보 (제공 코드만으로는 확정 불가)

1. **다시 점검 버튼에 닿을 수 있는지**: 점검 기록이 없고 조건만 달라진 경우, 토스트는 ‘다시 점검’을 누르라고 안내합니다. 그런데 `conditionView()`의 기록 없음 분기에는 버튼이 없습니다. 버튼이 다른 곳에 항상 보이지 않으면 사용자가 점검을 시작할 수 없습니다. VM 테스트는 `act('recheck')`로 DOM을 거치지 않아 이 문제를 잡지 못합니다.
2. **결과 본문 초기화**: `openMaterial`, `lessonSelect`, `material` 경로에는 `transientResult=''`가 보이지 않습니다. `hydrateMaterial`이 비우지 않으면 다른 자료의 검토문에 이전 자료의 결과 본문이 들어갑니다. 안내 문구(“전환하면 비워져요”)와도 어긋납니다. `hydrateMaterial`을 확인하고 테스트에 assert 한 줄을 추가하면 끝납니다.

## 비차단 (P2)

- 결과 이름을 입력하면 `live()`만 호출합니다. `conditionView`의 “점검 기록이 있어요” 문구는 다음 render까지 그대로 남습니다.
- `changeType`은 이제 호출되지 않는 코드인데, 옛 confirm 문구가 그대로 남아 있습니다. selftest가 이 함수를 검사하고 있다면 실제로 쓰는 경로가 아니라 죽은 경로를 검증하는 셈입니다.
- 다른 그룹으로 돌아갈 때 마지막 작업 대신 배열에서 마지막 수업을 엽니다. `lessonSelect`도 마지막으로 연 자료 대신 `materials[0]`를 엽니다.
- 짧은 요청(tab 2)을 복사해도 기록되지 않아, 이후 바뀐 조건 경고의 비교 기준이 실제와 다를 수 있습니다.

**결론**: 위 1과 2를 확인하고, 문제가 없으면 배포를 막을 오류는 보이지 않습니다.
