# 교사용 하네스 빌더 — 목적 중심 검토

검토 범위: 제공된 계획과 `index.html`(성취기준 데이터 배열 생략본), `tests/curriculum.test.cjs`만 읽었습니다. 코드는 실행하지 않았습니다. 1,040개 성취기준 원문, `tests/curriculum/sources.json`, 다른 테스트 파일, 배포 상태는 보지 못했습니다. 아래 버그는 코드를 읽고 추론한 것이라 재현으로 확인해야 합니다.

---

## (1) 목적 적합성 결론

**방향은 목적에 맞습니다. 다만 "컨텍스트 관리의 가치"를 보여 주는 핵심 근거 몇 가지가 아직 겉보기 수준이거나, 시간이 지나면 스스로 깨지는 구조입니다.**

잘 맞는 점:
- 계획 1절의 세 층 구분(맥락 관리 → 교사 운영 흐름 → 실행 하네스)은 "하네스와의 괴리"를 솔직하게 해소합니다.
- 실제 구현도 그 경계를 지킵니다. 수업 단위 공유 맥락, 자료 단위 상태, 요청 당시 조건 스냅샷, 조건 변경 경고가 있고, "복사 ≠ 실행", "파일 이름 ≠ 본문"이라는 안내도 지켜집니다.
- 성취기준 기능의 경계를 잘 그었습니다(3절). 차시 목표와 분리하고, 기본 설정·SKILL.md에 넣지 않고, 개정 연도를 명시적으로 고르게 했습니다.

목적과 어긋나는 점:
1. **점검 기록의 근거가 앱이 쓴 문장입니다.** 조건 스냅샷이 입력값이 아니라 렌더링된 요청 문장을 저장합니다(`conditionSnapshot`). 그래서 앱 문구를 고치거나 데이터를 교정해 배포하면 모든 교사의 점검이 "조건이 바뀌었어요"로 바뀝니다. 차별화의 핵심 증거가 배포마다 허위 경고를 냅니다.
2. **초보자 흐름에 데이터가 사라진 것처럼 보이는 경로가 있습니다.** 자료 종류를 다시 고르면 입력한 할 일이 비어 보입니다. 그런데 이 경로를 검증한다고 되어 있는 자체 점검은 UI에서 쓰지 않는 함수(`changeType`)를 테스트합니다.
3. **실제 교사 평가가 P2 뒤에 있습니다.** 검증되지 않은 가정 위에 P1·P2를 먼저 쌓는 순서입니다.
4. 계획의 P1·P2 일부(역할 5종 × 범위 2종, 5단계 작업 회차, `context.json`)는 "초보자 정보 부담 최소화"와 충돌할 위험이 큽니다.

## (2) 중요도 순 문제

### 높음

**H1. 점검 스냅샷이 입력값이 아닌 앱 문구를 비교함 → 배포할 때마다 모든 점검이 오래된 것으로 표시됨**
- 위치: `conditionSnapshot()`, `conditionsEqual()`, `staleCheck()`, `curriculumText()`, `referenceText()`, `gateList()` / 계획 6절 "조건 버전"
- 원인: `composition('create').blocks`에는 사용자 입력뿐 아니라 앱이 쓴 고정 문장이 섞여 있습니다. 예: "위 성취기준은 교육과정 원문입니다…", `QG_DEFAULTS`·`AUTO_RULES` 문장, 출처 URL. `conditionsEqual`은 이것을 `JSON.stringify`로 통째로 비교합니다.
- 실패 시나리오: 교사가 PPT를 점검해 "통과"를 기록합니다. 다음 배포에서 확인 기준 문장의 표현만 다듬습니다. 교사가 다음 날 열면 "이전 조건에서 확인 · 다시 확인해 주세요"가 뜨고, 표시를 하려 하면 "현재 조건으로 다시 점검을 먼저"가 나옵니다. 성취기준 원문 오탈자를 교정해도 같은 일이 생깁니다. CLAUDE.md의 "점검 조건의 실제 값과 버전을 보관한다"와도 어긋납니다.
- 수정안: 스냅샷에 정규화된 입력값을 저장합니다. 예: `{ctx, curriculum:{version, subject, codes, dataVersion}, skills, gates:{on, customText}, tools, reference:{source, textHash}, activity, out}`. 렌더링 텍스트는 표시용으로만 둡니다. 비교는 값끼리 하고, 바뀐 항목을 "학습 목표가 바뀜"처럼 값 단위로 보여 줍니다. 계획 P0의 "실제 값으로 비교"를 이 방식으로 구체화하세요. 기존 schema 4 스냅샷은 "이전 형식 · 값 비교 불가"로 이전합니다.

**H2. 자료 종류를 다시 고르면 할 일 입력이 사라진 것처럼 보이고, 빈 자료가 남음**
- 위치: VIEWS[0] 라디오 → `card change` → `openMaterial(type)`
- 원인: 처음에 PPT를 고르면 비어 있던 첫 자료가 PPT 자료가 됩니다. 이어서 할 일을 입력한 뒤 학습지로 바꾸면 `openMaterial`이 새 학습지 자료를 만들고, 그 자료의 `task`는 빈 값입니다(`empty`가 없으므로). 입력한 할 일과 형태·분량은 PPT 자료에 남아 있습니다.
- 실패 시나리오: 초보 교사가 잘못 누른 종류를 고치려다 방금 쓴 문장이 사라진 것을 봅니다. 동시에 수업·자료 바꾸기 메뉴에는 쓰지 않을 "수업 PPT" 버튼이 생깁니다.
- 수정안: 현재 자료에 결과·전달 기록·방법 수정이 아직 없으면(복사·점검 이력 없음), 새 자료를 만들지 말고 현재 자료의 종류만 바꿉니다. 할 일은 유지하고 방법만 다시 넣습니다. 이력이 있을 때만 별도 자료로 분기합니다.
- 함께 고칠 것: `changeType`, `newRequestState`, `case 'new'`, `case 'new-request'`, `hasInput`, `replacementNotice`는 UI에서 호출되지 않습니다. 그런데 `runSelfTests`의 "첫 종류 선택시 입력 보존", "새 요청의 상황 분리" 등이 이 함수들을 검증합니다. 자체 점검 통과가 실제 흐름을 보장하지 않습니다. 쓰지 않는 코드는 지우고, 테스트를 `openMaterial` 경로로 옮기세요.

**H3. 수업 자료에서 업무 문서로 오가면 가장 최근 업무에 자동으로 붙음 → 지난 업무의 확정 정보가 새 업무에 섞임**
- 위치: `openMaterial()`의 `previous=workspace.lessons.slice().reverse().find(...)`
- 원인: 업무 문서형의 `purpose`·`decided`·`reader`는 수업(lesson) 수준 맥락입니다. 그래서 수업 자료 → 업무 문서로 넘어가면 가장 최근 업무에 자동으로 합류합니다.
- 실패 시나리오: 10월에 현장체험 가정통신문을 만든 교사가 12월에 학습지를 만든 뒤 "업무 문서"를 고릅니다. 화면에 "10월 24일, ○○과학관, 도시락 지참"이 이미 채워져 있습니다. 전환 안내는 "…조건 적용"뿐이라 다른 행사의 날짜가 그대로 요청에 들어갈 수 있습니다. 예시 불러오기로 생긴 연습용 수업도 `previous` 후보가 되어, 교사 자료가 예시 수업에 들어갈 수도 있습니다.
- 수정안: 묶음(수업/업무)이 바뀔 때는 기본적으로 새 수업·업무를 만듭니다. 이전 것을 이어 가려면 "이전 업무 ‘현장체험학습 안내’ 이어서 하기"를 교사가 명시적으로 고르게 합니다. 예시로 만든 수업에는 `example:true`를 표시해 자동 후보에서 빼세요.

**H4. 출처 URL이 검색 결과 페이지라서 시간이 지나면 다른 문서를 가리킴**
- 위치: `CURRICULUM_SOURCES`의 NCIC 항목들(`result_more.do?search=…&page=3` 등). 이 URL은 `curriculumText()`를 통해 AI 요청문에도 들어갑니다.
- 실패 시나리오: NCIC에 자료가 추가되면 2페이지·3페이지의 내용이 밀립니다. 교사가 "공식 원문 확인"을 눌러도 원문을 찾지 못하고, 출처를 기록했다는 주장이 약해집니다.
- 수정안: 고시 번호와 별책 번호만 출처로 고정합니다. 링크는 고시 게시글 같은 영구 페이지나 NCIC 교육과정 원문 열람 경로로 바꿉니다. 그런 경로가 없으면 링크를 빼고 "NCIC에서 ‘국가교육위원회 고시 제2024-3호 별책 7’ 검색"이라는 안내 문구만 둡니다. AI 요청문에는 URL을 빼도 됩니다.

**H5. 데이터 검증 테스트가 출처 기록(sources.json)과 연결되지 않음**
- 위치: `tests/curriculum.test.cjs`
- 원인: 계획 3절은 "추출 파일 해시·과목별 개수는 sources.json에 기록"한다고 합니다. 그런데 테스트는 sources.json을 읽지 않고, 전체 1,040개와 24개 조합이 있는지만 확인합니다. PDF 추출에서 흔한 오류(한 기준 누락, 인접 기준 병합, 쪽 머리말·쪽번호 혼입)는 걸러내지 못합니다.
- 수정안(저비용):
  1. sources.json의 과목·연도별 기대 개수와 `CURRICULUM_DATA`의 실제 개수를 대조합니다.
  2. 코드 연번 검사: 같은 영역 접두어 안에서 `-01, -02…`가 빠짐없이 이어지는지 확인합니다. 누락과 병합을 대부분 잡습니다.
  3. 본문에 `[9`, `- 52 -`, `성취기준 해설`, 코드 패턴이 다시 나타나지 않는지 확인합니다(병합 탐지).
  4. 길이 상·하한을 둡니다.
  5. 과목마다 표본 3개를 PDF와 수동 대조하고 결과를 기록합니다.
- 함께 고칠 것: `curriculumText()`는 "교육과정 원문입니다"라고 쓰지만, 수록 범위 안내는 "띄어쓰기·줄바꿈은 정리"했다고 합니다. 요청문은 "원문(공백만 정리)"으로 맞추세요.

### 중간

**M1. 2026학년도 적용 안내가 고정 문구라 2027년에 틀린 안내가 됨**
- 위치: `curriculumView()`의 "2026학년도: 중1·2는 2022 개정, 중3은 2015 개정"
- 2027학년도에는 중1~3 모두 2022 개정입니다. 연도는 `new Date()`로 계산하고, 적용 표(2025 중1, 2026 중2, 2027 중3)를 `NOTICES`에 둡니다.
- 초보자 부담을 줄이는 방법: 학년 입력과 올해 연도로 추천 개정 연도를 "추천: 2022 개정 (중2 · 2026학년도)"처럼 보여 주고, 선택은 교사가 하게 합니다. 3절의 "학년만으로 확정하지 않는다"는 지키면서 고를 것을 하나 줄입니다.

**M2. 점검 기록이 계속 쌓여 결국 자동 저장이 멈춤**
- 위치: `archiveCheck()`, `MAX_WORKSPACE=1500000`
- 원인: `checkHistory` 한 건에는 스냅샷 전체가 들어갑니다(참고 발췌 최대 6,000자 + 성취기준 + 방법). 그리고 다음 경우마다 새로 쌓입니다:
  - 결과 이름을 처음 고칠 때(`data-meta=resultName` 입력)
  - 새 결과로 점검 시작
  - 현재 조건으로 다시 점검
  - `applyFixes`
- 실패 시나리오: 한 학기 사용하면 1.5MB를 넘고, 이후 모든 저장이 "저장하지 못했어요"가 됩니다. 이 상태에서는 백업 복원(가져오기)도 없습니다.
- 수정안: 자료별로 최근 N개(예: 10개)만 남기고, 스냅샷은 H1의 값 형식으로 줄입니다. 발췌 본문은 해시만 저장합니다.
- 함께 고칠 것: 결과 이름의 오타만 고쳐도 표시한 점검이 모두 기록으로 넘어가 사라집니다. 이름 변경과 새 결과는 버튼으로만 구분하세요.

**M3. 이전 점검 기록이 JSON 원문으로 표시됨**
- 위치: VIEWS[6]의 `check-history` 상세 영역. 현재 `{"fact":"o"}`와 ISO 시각을 그대로 출력합니다.
- 수정안: "사실 정확성 통과 · 학생 수준 수정 필요 · 10월 18일 14:20"처럼 사람이 읽는 형태로 바꿉니다.

**M4. 백업은 내려받기만 되고 복원이 없음 → P1이 아니라 P0 과제**
- 저장 실패·다중 탭 충돌 때마다 "작업 보관 파일을 내려받아 주세요"라고 안내하지만, 다시 불러오는 경로가 없습니다. P1에서 데이터 구조가 바뀌기 전에 가져오기를 먼저 넣어야 이전 경로가 생깁니다.
- 가져오기에 필요한 것: 검증(`bootWorkspace`의 검증 로직 재사용), 미리보기, 덮어쓰기 대신 수업 추가.

**M5. "우선 세 가지만"이라는 안내와 실제 화면이 다름**
- 위치: `STEPS[1].easy`, VIEWS[1], `UI.primaryFields.lesson=['grade','cur','goal']`
- 실제로 처음 보이는 칸은 과목·학년·교육과정(접힘)·학습 목표·활동 다섯 개입니다. `primaryFields`에 있는 `cur`(이번 차시)는 "분량·자료 등" 안에 숨어 있습니다. 그래서 `lessonLabel()`이 `cur`를 수업 이름으로 먼저 쓰지만, 대부분의 교사는 이 칸을 채우지 않습니다.
- 문구, `primaryFields`, `summaryView`의 누락 판정을 하나로 맞추세요.

**M6. 참고자료 입력이 두 곳으로 나뉨**
- `CONTEXT_FIELDS.lesson`의 `ref`(참고자료) 칸과 `referenceView()`의 출처·발췌가 따로 있고, `referenceText()`는 둘을 섞어 씁니다.
- 수록되지 않은 과목은 성취기준을 참고 발췌에 붙여 넣으라고 안내하는데, 발췌 칸이 하나뿐이라 교과서 발췌와 자리를 다툽니다.
- P1 이전에 `ref` 칸을 없애고 출처 칸 하나로 합치세요. 수록 밖 과목에는 "성취기준 직접 붙여넣기" 칸을 따로 둡니다. 이 칸은 `curriculumText`에 "교사가 붙여 넣음 · 앱이 원문 검증하지 않음"으로 표시합니다.

**M7. 접근성: "5개 더 보기"를 누르면 초점을 잃음**
- 위치: `case 'standard-more'`가 `#standardsResults` 내부 HTML을 통째로 다시 그립니다. 버튼이 사라지면서 초점이 문서 처음으로 갑니다.
- 키보드·화면 낭독기 사용자는 위치를 잃습니다. 새로 나타난 첫 항목의 "기준 추가" 버튼으로 초점을 옮기세요.
- 같은 문제: "기준 추가" 후에는 초점이 검색창으로 가는데, 무엇이 담겼는지 알려 주는 상태 알림이 없습니다.

**M8. 디자인 규칙이 CLAUDE.md와 어긋난 상태로 기록 없음**
- CLAUDE.md는 "포인트 색은 남색 #1F2A44 하나"라고 하는데, 현재는 청록 `#0f766e`, 연보라, 아이콘별 색입니다. 셀렉트 화살표 SVG는 여전히 `%231F2A44`입니다.
- 사용자가 색을 요청했으므로 바꾼 것 자체는 정당합니다. 다만 CLAUDE.md의 "명세와 다르게 정한 것"에 새 색 역할(행동=청록, 보조=연보라, 경고=주황)을 기록하고, 화살표 색도 맞추세요. 계획 2절의 "강조색 역할 일관성"이 이것입니다.

### 낮음

- **L1. 요청문에 교사에게 할 말이 섞임.** `curriculumText`의 "학년별 배치는 학교 교육과정을 확인하세요"는 AI에게 보내는 문장으로 어색합니다. "학년별 배치는 제공되지 않았으니 임의로 정하지 마세요"로 바꾸세요.
- **L2. 성취기준을 고르지 않았는데 블록이 생김.** 개정 연도만 고른 상태에서는 "과목 미선택 + 아직 선택하지 않았습니다" 블록이 매번 요청에 들어갑니다. 연도와 과목을 모두 정했을 때만 한 줄짜리 안내를 넣으세요.
- **L3. 검색 상태가 전환 후에도 남음.** `curriculumQuery`와 `curriculumVisible`이 전역 변수라 수업·자료를 바꿔도 이전 검색어가 남습니다.
- **L4. 예시 드롭다운 선택이 되돌아감.** `#exampleType`이 `render()`마다 `state.type`으로 돌아가 교사가 고른 값이 바뀝니다.
- **L5. 직접 입력 과목 칸이 확인을 거치지 않음.** `customSubject` 입력은 `setCurriculumContext`를 거치지 않으므로, 기준을 담은 뒤 과목명을 고치면 확인 없이 불일치 상태가 됩니다. 불일치는 `curriculumIssue`가 복사를 막아 복구할 수 있으므로 낮음입니다.
- **L6. 새 수업에서 개정 연도를 다시 골라야 함.** `startLesson()`이 과목은 복사하지만 개정 연도는 복사하지 않습니다. 성취기준은 복사하지 않는 것이 맞지만, 개정 연도는 같은 교사·같은 학년이면 대개 같습니다. 복사하고 "가져온 정보"에 표시하는 편이 초보자 부담을 줄입니다.
- **L7. 가치를 보여 줄 예시가 성취기준을 쓰지 않음.** 예시들에 성취기준 선택이 없습니다. 평가문항 예시의 규칙은 오히려 "코드는 제공받지 않았다면 임의로 만들지 않는다"입니다. 시범 예시 하나(평가문항)에는 실제 기준 1개를 미리 담아 두면, "한 번 고르면 다른 자료에도 유지"를 교사가 바로 볼 수 있습니다.

## (3) 과잉 설계와 빠진 의존성

**과잉 설계 (초보자 부담 또는 검증 전 투자):**
- **P1 `context.json` 별도 내려받기:** 초보 교사가 이 파일로 할 일이 없습니다. 요청문 하나에 발췌를 포함하고, 첨부할 원본 목록을 요청문 끝에 적는 것으로 충분합니다.
- **P1 파일 역할 5종 × 범위 2종:** 파일마다 고를 것이 두 개씩 생깁니다. 기본값을 "수업 공통 · 역할 미지정"으로 두고, 바꾸는 것은 접힌 영역에서만 하세요.
- **P2 작업 회차 5단계 상태 머신:** 내부 상태로는 괜찮지만, 화면에는 "다음에 할 일" 한 줄만 보이게 하세요. 단계 이름을 보여 주면 교사가 상태를 관리해야 합니다.
- **P2의 판단 주체 3종(교사/외부 AI/자동 검사):** P3 전에는 자동 검사가 없습니다. 지금은 교사와 외부 AI 의견 두 가지로 충분합니다.
- **P2 병행 9개 유형별 평가 예제:** 유형별로 작업 절차가 실제로 다르다는 것을 먼저 보여 주는 게 우선입니다. 예제는 교사 평가에서 쓰이는 3개 유형(PPT·학습지·평가문항)부터 시작하세요.

**빠진 의존성:**
1. **데이터 구조 이전 계획:** P1에서 `reference`가 `references[]`로 바뀌면 schema 5 이전과 테스트가 필요한데 계획에 없습니다. M4의 가져오기와 H1의 값 스냅샷이 선행 조건입니다.
2. **성취기준 데이터 버전:** 데이터를 교정하면 저장된 선택과 요청 기록이 가리키는 문장이 달라집니다. 데이터 버전(`dataVersion`)을 선택과 스냅샷에 저장해야 "데이터가 갱신됨"과 "교사가 조건을 바꿈"을 구분할 수 있습니다.
3. **HWP·HWPX 현실:** 한국 교사 파일의 대부분은 HWP/HWPX·PPTX·PDF입니다. TXT/MD만 지원하면 P1의 실효성이 낮습니다. HWPX·DOCX·PPTX는 ZIP 안의 XML이라, 브라우저 기본 기능(`DecompressionStream('deflate-raw')`)만으로 외부 라이브러리 없이 텍스트를 뽑을 수 있습니다. 단일 HTML 제약 안에서 PDF보다 먼저 검토할 가치가 있습니다. 구형 바이너리 `.hwp`는 제외하고 원본 첨부 안내를 유지하세요.
4. **결과 지문은 파일 읽기가 선행 조건:** P2의 "내용 지문/파일 속성"은 결과 본문을 저장하지 않는 현재 정책(80,000자, 저장 안 함)과 P1의 파일 읽기에 묶여 있습니다. 계획에 명시하세요.
5. **교사 평가 시점:** 9절의 과업 ③④는 P1·P2 기능을 전제로 하는데, 평가는 그 뒤에 배치되어 있습니다. 지금 있는 기능으로 1차 평가를 먼저 하세요.
6. **배포 제외 확인:** `tests/curriculum/`은 아직 Git에 올라가지 않은 상태로 보입니다. Firebase 제외 규칙이 이 폴더도 덮는지(`/tests/curriculum/sources.json` 404) 배포 검수에 추가하세요.
