# 검토 결과: 재사용 지침·스킬 설정 요청 옵션

전반적으로 통과에 가깝습니다. 재귀 호출은 없고, 재사용 스킬과 이번만 쓰는 정보도 분리되어 있습니다. 다만 제작이 멈출 수 있는 문제 1건과 전역 저장 위험 1건은 고치고 출시하는 편이 좋겠습니다.

제가 본 것은 전달받은 diff와 함수뿐입니다. `fill`, `syncRules`, `handoffSteps`, `workflowText`, `lastTransfer` 기록 코드는 보지 못했고, 아무것도 실행하지 않았습니다.

## 중요도 중간

**1. AI가 덮어쓰기 확인을 기다리며 제작을 멈출 수 있음 (기준 3)**
- `TEMPLATES.setup`의 2단계는 "다른 내용의 기존 스킬…덮어쓰지 말고 차이를 알려 확인받으세요"입니다. 반면 첫 문단과 7단계는 제작을 계속하라고 합니다. 에이전트형 AI는 확인을 받으려고 응답을 끝낼 가능성이 큽니다.
- 그런데 같은 이름에 다른 내용이 오는 상황이 자주 생기게 되어 있습니다.
  - `skillName=()=>teacher-${state.type}`은 자료 유형만으로 이름을 정합니다. 과학 학습지와 수학 학습지가 같은 이름이 됩니다.
  - `reuse.title`은 `state.ver>1`이면 `(v2)`를 붙이므로 버전이 오를 때마다 내용이 달라집니다.
  - `skillList(v,true)`의 `activeAuto(v)`와 `gateList(v,true)`의 `qgOn(k,v)`는 이번 요청의 값(`v`)으로 켜고 끕니다. 그래서 같은 수업 안에서도 이번 요청에 오개념이나 참고자료가 있느냐에 따라 스킬 본문이 달라집니다. 사적인 정보가 새는 것은 아니고, 내용이 흔들리는 문제입니다.
- 제안(문구만 수정): "기존 것은 그대로 두고 이번 대화에만 적용한 뒤 제작을 계속하고, 차이는 상태 보고에 한 줄로 남기세요."
- 이름 충돌을 줄이려면 skillName에 교과처럼 고정된 값을 넣는 방법이 있습니다. 다만 이건 범위 판단이라 선생님의 결정이 필요합니다.

**2. 전역 설정 금지 문장이 2단계에만 있음 (기준 2)**
- "전역 설정 변경이나…설치는 포함되지 않습니다"는 2단계 안에만 있습니다.
- 3단계의 "프로젝트 지침을 저장하는 기능"을 ChatGPT의 메모리처럼 모든 대화에 적용되는 저장소로 해석할 여지가 있습니다.
- 제안: 이 금지 문장을 1~4단계 전체에 적용되는 공통 조건으로 옮기세요. 예: "사용자 전체 메모리·맞춤 설정에는 저장하지 마세요."
- 덜 흔한 경우: Claude Code를 홈 폴더에서 실행하면 "현재 작업 공간"이 사용자 전역 스킬 폴더(`~/.claude/skills`)와 같아집니다.

**3. 이미 저장된 자료와 새 자료의 기본값이 켜짐으로 바뀜 (기준 5)**
- `load()`가 기존 schema 3 자료에 `setupReusable=true`를 넣습니다. 그래서 이미 쓰던 자료의 요청문에도 큰 설정 블록이 갑자기 붙습니다. CLAUDE.md의 원칙 두 가지와 부딪힐 수 있습니다.
  - "이전한 자료의 선택은 바꾸지 않는다"
  - "스킬 내보내기는 펼칠 때만"
- 선택값은 자료마다 따로 저장됩니다(`blank()`). 그래서 선생님이 꺼 두어도 "이 수업·업무로 다른 자료 만들기"를 누르면 다시 켜집니다.
- "기본 체크"를 요청하셨으니 의도된 동작일 수 있습니다. 기존 자료에도 켜는 것까지 의도했는지는 확인이 필요합니다.

## 중요도 낮음

**4. 일반 채팅에서 원문을 다시 출력할 수 있음 (기준 3)**
- 4단계의 "그마저 불가능하면 복사 가능한 원문을 제공"을 따르면, 일반 채팅은 긴 스킬 원문 전체를 한 번 더 출력합니다.
- 앱에 이미 '스킬만 다운로드'가 있으므로 "원문을 다시 출력하지 말고, 앱의 스킬 파일을 쓰라고 안내"로 줄일 수 있습니다.

**5. `composition('create')`가 상태를 바꾸고 계산을 버림 (기준 4)**
- 이제 `composition('create')` 안에서 `setupRequest`를 거쳐 `reusableOutputs`, `syncRules(state)`까지 불립니다. 화면을 그리는 경로(`outputSummary`, `conditionSnapshot`, `conditionMessage`)에서 상태가 바뀌는 셈입니다.
- `conditionSnapshot`은 설정 블록을 만든 다음 바로 걸러 버립니다.
- `syncRules`가 같은 결과를 반복해도 문제가 없다면 실제 영향은 없습니다. 그래도 snapshot에서는 setup 블록을 처음부터 만들지 않는 편이 안전합니다.

**6. `fill` 구현에 따라 사용자 문장이 깨질 수 있음 (미확인)**
- `fill(TEMPLATES.setup,{skill})`에서 `{skill}`에는 사용자가 쓴 규칙이 들어갑니다.
- `fill`이 문자열 replacement 방식이면 규칙 속의 `$&`, `$'`가 특수 패턴으로 해석됩니다. 다시 훑는 방식이면 규칙 속의 `{type}`이 값으로 바뀝니다.
- 제안: 이 두 문자열을 넣은 규칙으로 테스트 한 줄을 추가하세요.

**7. UI 문구 (기준 6)**
- `setupHelp`의 "일반 채팅은 이 대화에 적용해요"는 앱이 보장하는 것처럼 읽힙니다. "이 대화에만 적용하도록 요청해요"가 더 정확합니다.
- `reuseChoices`의 "AI 설정에 선생님이 직접 저장하는 규칙"과 새 옵션(AI가 저장 시도)이 서로 다른 경로를 안내합니다. 두 가지를 모두 하면 규칙이 중복될 수 있습니다.
- 대화에만 적용된 경우, 이후 짧은 요청문("저장된 기본 설정에 맞춰…")은 새 채팅에서 동작하지 않습니다. 이 점을 짧게 알려 주는 안내가 있으면 좋습니다.

## 통과

- **기준 1 (실제 파일과 등록·인식 구분):** 상태 4종 보고, 다시 읽어 확인, "활성화 미확인", "앱에 자동 전달 안 됨" 문구가 모두 있습니다.
- **기준 2 (스킬 내용):** 스킬 템플릿의 자리값은 모두 `rv`나 reusable 값으로 덮입니다(`tools`만 예외이며 민감하지 않음). 이번 요청 범위의 규칙·기준, 성취기준, 교과서 발췌는 빠지고, 테스트도 이를 확인합니다. 백틱 수를 계산해 코드 블록이 깨지지 않게 한 처리도 맞습니다.
- **기준 4 (상태 분리):** 재귀 호출은 없습니다. 실제 전달 기록(`lastTransfer`)에는 설정 블록을 남기고 제작 요청 기록(`lastRequest`)과 점검 snapshot에서는 뺀 것이 적절합니다. 설정 블록은 결과물 내용과 무관하므로 체크를 켜고 꺼도 점검이 오래된 것으로 표시되지 않습니다. 검토·이어하기의 '바뀐 조건' 비교도 일관됩니다.
- **기준 5 (경로 회귀):** 설정 블록은 제작(create) 요청에만 붙고 수정·이어하기·검토에는 붙지 않습니다. 복사한 내용과 화면 출력이 일치합니다. 스킬 단독 다운로드는 그대로입니다.

## 테스트가 덮지 않는 부분

- 업무 그룹의 `oneOff` 문구
- `ver>1`일 때와 같은 유형 이름 충돌
- 기존 자료를 불러와 이전할 때 기본값이 켜지는 것
- 6번의 `$`, `{}` 문자열
